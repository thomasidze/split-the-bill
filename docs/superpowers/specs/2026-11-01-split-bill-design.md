# Сплит счёта в Telegram — дизайн

Дата: 2026-11-01
Статус: на согласовании

## 1. Цель

Telegram Mini App для деления общих расходов внутри компании друзей.
Делается для себя и друзей: приоритет — удобство и надёжность, без монетизации
и без расчёта на тысячи пользователей.

Разработчик — начинающий, знает Python поверхностно. Поэтому стек — почти
целиком Python, код должен быть простым и читаемым.

### Критерии успеха

- Бота добавили в групповой чат → любой участник чата открывает приложение и видит события этого чата.
- Можно создать событие («Баня 21.06»), добавить в него расходы с позициями и фото чека.
- Каждый отмечает свои позиции; везде видно, сколько денег ещё не разобрано.
- По событию видно, кто кому сколько должен, с минимумом переводов; переводы подтверждаются.
- Суммы сходятся до копейки.

### Вне рамок (пока)

- Распознавание позиций с фото чека (OCR) — следующий этап.
- Несколько валют — только рубли.
- Повторяющиеся траты, напоминания по расписанию, монетизация.
- Использование приложения вне групповых чатов (в личке с ботом).

## 2. Сценарии и экраны

### Подключение к чату

1. Бота добавляют в групповой чат.
2. Бот создаёт для чата запись в базе со случайным кодом (`invite_code`) и пишет
   приветствие с URL-кнопкой «Открыть» → `https://t.me/<bot>/<app>?startapp=<invite_code>`.
   Сообщение предлагается закрепить.
3. Команда `/app` в чате повторно присылает это сообщение.

Приложение всегда открывается в контексте одного чата: код чата приходит в `start_param`.

### Главный экран чата

- Название чата.
- Список событий (новые сверху): название, общая сумма, «не разобрано N ₽»,
  личный итог пользователя («ты должен 1 350 ₽» / «тебе должны 4 200 ₽» / «в расчёте»).
- Кнопка «Новое событие» (MainButton) → ввод названия → создатель автоматически становится участником.

### Экран события

- Название, участники (аватарки/имена), кнопка «Я участвую» (если пользователь ещё не участник).
- Вкладка **Расходы**: список расходов — название, кто платил, сумма,
  «не разобрано N ₽ из M ₽», статус (открыт/закрыт). Сверху — суммарно «не разобрано» по событию.
- Вкладка **Кто кому**: список переводов после взаимозачёта (см. §3.6).
  У должника — кнопка «Я перевёл», у получателя — «Подтвердить» на ожидающих переводах.
- MainButton «Добавить расход».

### Добавление расхода

Поля:
- Название (обязательно).
- Кто платил — по умолчанию текущий пользователь, можно выбрать другого участника события.
- Позиции: название, цена за штуку (₽, до копеек), количество (по умолчанию 1),
  флажок «на всех». Минимум одна позиция.
- Чаевые, % — 0 / 5 / 10 / 15 / своё (по умолчанию 0).
- Фото чека — необязательно.

После сохранения автор и плательщик становятся участниками события,
бот пишет в чат уведомление (см. §4.4).

Редактировать и удалять расход может только его автор и только пока расход открыт.
При удалении позиции удаляются и отметки на ней. Если у позиции уменьшили количество
ниже числа отмеченных штук — работает правило «отмечено больше, чем есть» (§3.2).

### Экран расхода (отметка позиций)

- Шапка: название, кто платил, итог с чаевыми, фото чека (по нажатию — крупно).
- Строка «Не разобрано: N ₽ из M ₽».
- Список позиций. У каждой: название, цена × количество, кто отметился (имена и штуки).
  - Позиция на 1 штуку: переключатель «Моё» (вкл/выкл).
  - Позиция на несколько штук: «−  k  +» — сколько штук берёт текущий пользователь.
  - Позиция «на всех»: отметки нет, подпись «делится на всех (n чел.)».
- Блок «Твоя доля: X ₽ (включая чаевые Y ₽)».
- Отметка позиции автоматически делает пользователя участником события.
- Данные обновляются опросом раз в 5 секунд, пока экран открыт.
- У плательщика — кнопка «Закрыть расход» (см. §3.5).
- Виброотклик при отметке.

## 3. Модель данных и расчёты

### 3.1 Таблицы

| Таблица | Поля |
|---|---|
| `chats` | `id` (Telegram chat_id), `title`, `invite_code` (уникальный, случайный), `bot_active`, `created_at` |
| `users` | `id` (Telegram user_id), `first_name`, `last_name`, `username`, `photo_url`, `updated_at` |
| `events` | `id`, `chat_id`, `title`, `created_by`, `created_at` |
| `event_participants` | `event_id`, `user_id` (PK из двух) |
| `expenses` | `id`, `event_id`, `title`, `payer_id`, `created_by`, `tip_percent` (целое), `photo_file_id` (nullable), `status` (`open`/`closed`), `leftover_mode` (`split`/`payer`, nullable до закрытия), `created_at`, `closed_at` |
| `items` | `id`, `expense_id`, `name`, `unit_price` (копейки), `qty` (≥1), `for_all` (bool) |
| `claims` | `item_id`, `user_id`, `units` (≥1) (PK из двух) |
| `settlements` | `id`, `event_id`, `from_user`, `to_user`, `amount` (копейки), `status` (`pending`/`confirmed`), `created_at`, `confirmed_at` |

Все деньги — целые копейки.

### 3.2 Доля по позиции

Пусть позиция стоит `T = unit_price × qty`, отмечено всего `U = Σ units` штук.

- `U ≤ qty`: каждый платит `units × unit_price`; не разобрано `(qty − U) × unit_price`.
- `U > qty`: вся сумма `T` делится пропорционально `units`; не разобрано 0.
- `for_all`: `T` делится поровну между текущими участниками события; не разобрано 0.

### 3.3 Округление

Любое деление суммы на части — методом наибольшего остатка: каждому округление вниз,
оставшиеся копейки раздаются по одной тем, у кого дробные остатки больше
(при равенстве — по возрастанию `user_id`). Сумма частей всегда равна исходной сумме.

### 3.4 Чаевые

Доля пользователя по расходу = `items_share × (100 + tip_percent) / 100`.
Чаевые со всего разобранного распределяются пропорционально `items_share` тем же
методом наибольшего остатка. «Не разобрано» тоже показывается с чаевыми.

### 3.5 Закрытие расхода

Только плательщик. Если не разобрано > 0 — диалог:
- «Поделить поровну между участниками события» (`leftover_mode = split`) — остаток
  (с чаевыми) делится поровну на всех участников события, включая плательщика;
- «Оставить на мне» (`leftover_mode = payer`) — остаток никому не начисляется.

После закрытия отметки и позиции не меняются.

### 3.6 Балансы и «Кто кому»

По каждому расходу каждый участник, кроме плательщика, должен плательщику свою долю.
Неразобранное у открытого расхода никому не начисляется.

Баланс пользователя в событии = (сколько должны ему) − (сколько должен он)
+ (подтверждённые переводы, которые он отправил) − (подтверждённые, которые получил).

Список переводов: жадно — наибольший должник платит наибольшему кредитору
`min(|долг|, кредит)`, повторять до нуля. Переводов ≤ (участников − 1).

«Я перевёл» создаёт `settlement` со статусом `pending` на сумму рекомендованного перевода.
На баланс влияет только после «Подтвердить» получателем. Ожидающие переводы
показываются отдельно с пометкой «ожидает подтверждения».

## 4. Техническая часть

### 4.1 Стек

- Python 3.12+, FastAPI, Uvicorn.
- aiogram 3 — бот, получает обновления через вебхук в том же приложении.
- SQLAlchemy 2 + SQLite (файл на постоянном диске).
- Jinja2-шаблоны + htmx + `telegram-web-app.js` (официальный скрипт Telegram).
- CSS на переменных темы Telegram (`--tg-theme-*`), без CSS-фреймворков.
- pytest для тестов.

### 4.2 Структура проекта

```
app/
  main.py        — создание FastAPI, подключение роутов и вебхука бота
  config.py      — настройки из .env (BOT_TOKEN, APP_URL, BOT_USERNAME, APP_SHORT_NAME, DB_PATH)
  db.py          — подключение к базе, сессии
  models.py      — таблицы
  auth.py        — проверка initData, проверка членства в чате
  calc.py        — чистые функции расчёта (§3.2–3.6), без базы и сети
  services.py    — загрузка данных из базы и вызов calc.py
  bot.py         — обработчики бота и функции отправки уведомлений
  routes/
    pages.py     — HTML-страницы и фрагменты для htmx
templates/
static/
tests/
```

### 4.3 Аутентификация

- Оболочка страницы (`GET /`) не содержит данных. Скрипт берёт `Telegram.WebApp.initData`
  и `start_param` и подставляет их заголовками (`X-Init-Data`) во все htmx-запросы.
- Каждый запрос: проверка подписи `initData` по алгоритму Telegram (HMAC-SHA256 с ключом
  от `BOT_TOKEN`), `auth_date` не старше 24 часов. Иначе — экран «Открой приложение заново из чата».
- Чат определяется по `invite_code` из `start_param`. Членство проверяется через
  `getChatMember` (статусы member/administrator/creator/restricted), результат кешируется в памяти на 5 минут.
  Не участник → «Это событие доступно только участникам чата».
- Данные пользователя (имя, username, фото) обновляются в `users` при каждом входе.

### 4.4 Бот

- `my_chat_member` (бота добавили в группу) → создать/активировать `chats`, отправить приветствие.
  Бота удалили → `bot_active = false`; данные сохраняются, но приложение показывает
  «Бот удалён из чата — добавьте его обратно» (без бота нельзя проверить членство).
  При повторном добавлении — тот же `invite_code`, все данные снова доступны.
- `/app` в группе → повторить приветствие.
- Новый расход → сообщение в чат: «<Имя> добавил(а) расход «<название>» в «<событие>»: <сумма> ₽. Отметьте свои позиции»
  + URL-кнопка с `startapp=<invite_code>_e<expense_id>` (сразу на экран расхода).
  Если есть фото — отправляется как фото с этой подписью.
- Загрузка фото: файл приходит на сервер, бот отправляет его в чат (`sendPhoto`),
  сохраняется только `file_id`. Показ в приложении — через эндпоинт, проксирующий файл
  из Telegram (`getFile`), с проверкой доступа к чату.
- Ошибка отправки сообщения в чат не мешает сохранению расхода (логируется).

### 4.5 Деплой

- Разработка: локальный запуск + туннель (cloudflared) для HTTPS-адреса; его прописываем в BotFather и как вебхук.
- Прод: хостинг с HTTPS и постоянным диском под SQLite (VPS или PaaS с volume). Конкретный выбор — в плане.
- Ручные шаги пользователя: создать бота в @BotFather, зарегистрировать Mini App (`/newapp`),
  заполнить `.env`. В README — пошаговая инструкция.

## 5. Тестирование

- `tests/test_calc.py` — главное: позиции (≤qty, >qty, for_all), округление, чаевые,
  закрытие (split/payer), балансы с подтверждёнными/ожидающими переводами, взаимозачёт;
  инвариант «сумма долей + неразобранное = сумма расхода» на всех случаях.
- `tests/test_auth.py` — валидная/подделанная/просроченная подпись initData.
- `tests/test_pages.py` — основные сценарии через TestClient с подписанным тестовым initData
  и замоканными вызовами Telegram (членство, отправка сообщений).
- Ручная проверка в реальном Telegram-чате через туннель.
